# Отчёт: этап визуализации и тестирования MVP — ӘЙДӘ ИНДЕ!

Репозиторий: https://github.com/aliseemore-dotcom/aidainde (`main`, коммит `f4e196d`). Дата: 22.10.2026.

## 1. Контекст
Сервис подбирает досуг в Казани: короткий тест → детерминированная подборка из собственного каталога (без нейросетей) + свободный каталог мест и событий. Стек: Next.js, TypeScript, Postgres (Supabase) + Drizzle, Zod, Vitest, Playwright. Дизайн — по дизайн-киту «ӘЙДӘ ИНДЕ!».

Задача этапа: довести существующий интерфейс до состояния, когда можно пройти полный путь «главная → тест → результаты → карточка» и оценить продукт на уже собранных данных (69 заведений, 64 события), не расширяя каталог и не добавляя фото.

## 2. Что было не так (проверка текущего состояния)
Тесты и сборка были зелёными, но **посмотреть продукт на реальных данных было нельзя**: все собранные записи — черновики, а черновики нигде не показывались (только отдельная карточка вошедшему редактору). Каталог и подборка были пустыми. Плюс мелочи интерфейса, мешавшие оценке (карточки без адреса и описания, вкладка каталога по умолчанию с малым числом данных, пустые «Цена уточняется»).

### Режим предпросмотра черновиков
- Включается переменной `PREVIEW_DRAFTS=true` и **никогда не работает на боевом деплое** (`VERCEL_ENV`/`APP_ENV=production`) — проверено тестом.
- Показывает черновики в каталоге, подборке и карточках с чёткой пометкой: плашка «Режим предпросмотра» сверху, «Черновик: данные не проверены» на карточках.
- В этом режиме события без даты проверки участвуют в подборке (в обычном режиме нет). По умолчанию (флаг выключен) посетители не видят ни одного черновика.
- Подготовленные данные лежат в `content/preview/` (заведения и события). Локально они сами загружаются во встроенную базу.

Запуск на своём компьютере (Node 22+):
```bash
git clone https://github.com/aliseemore-dotcom/aidainde.git && cd aidainde
npm install
echo "PREVIEW_DRAFTS=true" > .env.local
npm run dev            # http://localhost:3000
```

## 6. Проблемы, которые действительно мешают запуску
1. **Нет публичной ссылки на работающую версию.** Приложение работает только внутри моей облачной среды. Для ссылки нужны: проект Supabase (строка подключения `DATABASE_URL`), аккаунт Vercel с подключённым репозиторием и домен. Пока смотреть можно локально (раздел 3) или по скриншотам.
2. **У событий нет площадок.** Все 64 события ссылаются на три площадки (театр Камала, филармония имени Тукая, зал имени Сайдашева), которых в каталоге нет (нужны адреса и источники). Поэтому в карточках события не показываются площадка и адрес.
3. **Данные заведений минимальны.** Описания шаблонные и повторяют адрес; из тегов только «Заведения» и «Еда и разговоры» (нет настроения, состава компании, энергии); нет дат проверки, цен, часов и фото. Подборка работает, но по заведениям различается слабо.
4. **Нет признака «на улице/в помещении» (`indoorOutdoor`).** Из-за этого просьба «на улице» может вернуть концерты в залах. Достаточно указать `indoor` у событий и площадок.
5. **Не указаны возрастные ограничения событий.** Некоторые спектакли могут иметь ограничения; подбор исключает такие записи для семей с детьми только при известном `ageMin`.
6. **Все события и заведения — черновики и без даты проверки** (`verifiedAt`). Публикация в админке без неё недоступна, и в подборку обычного режима они не попадут. Это сознательное решение; нужна сверка у организаторов и дата.
7. **Вход Supabase Auth в админку не проверен вживую** (нет ключей); весь остальной сценарий редактора проверен в браузере.
8. Текст политики данных рабочий, нужна юридическая редакция; мониторинг ошибок не подключён.

## 7. Что дальше
1. Передать ключи Supabase и аккаунт Vercel → деплой и ссылка на работающую версию.
2. Прислать данные трёх площадок → загрузить площадки, затем события (привязка по `placeSlug`).
3. Дополнить данные: теги (настроение, компания, энергия), `indoorOutdoor`, возрастные ограничения, даты проверки.
4. Опубликовать проверенное через админку, запустить `npm run content:check`.

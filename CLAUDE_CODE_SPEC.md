# Куда сегодня? — архитектура веб-сервиса досуга в Казани

**Версия:** 1.0 • **Дата:** 12.10.2026 • **Статус:** архитектура MVP / техническое задание для Claude Code

> Этот документ — источник истины для реализации. Не придумывай новые ветки, ответы и бизнес-правила без фиксации в конфигурации, тестах и документации. Если параметр не определён, следуй явно описанному безопасному поведению. Контент каталога не выдумывать.

## 0. Продукт и границы

**Цель.** Помочь человеку найти занятие в Казани исходя из сегодняшнего настроения, состава компании, желаемой атмосферы, места, даты и бюджета. Ответ — персональная подборка существующих и доступных активностей, а не абстрактная беседа с нейросетью.

**Первый экран:** заголовок «Хм, чем бы заняться в Казани?» и три равноправные карточки: (1) «Подбери мне досуг» (`/quiz`); (2) «Хочу выбрать сам» (`/explore`); (3) «У меня сегодня свидание» (`/date`). Слово «сегодня» в заголовке — маркетинговый текст: выбор фактической даты происходит в сценарии.

**Границы MVP:** полностью реализовать главный тест, результаты, каталог мест и мероприятий, сохранение контента через admin, публичный просмотр карточек и поиск/фильтры. Маршрут `/date` — отдельная красивая заглушка «Скоро запустим», без заимствования вопросов основного теста; проект предусмотреть для последующего независимого DateQuiz. Telegram-бот, бронирования, платежи, личные кабинеты пользователей и автоматический парсинг сайтов — вне MVP. Дизайн реализуется Claude Code параллельно функционалу; мобильная версия первична.

**Критический принцип:** AI может быть добавлен позже для объяснения результатов или свободного запроса, но НЕ определяет переходы вопросов и не сочиняет карточки каталога. Рекомендации MVP детерминированы.

## 1. Целевая аудитория и пользовательские истории

- Человек один: «Сегодня хочется тишины и нового впечатления» → маршрут, выставка, камерная активность.
- Двое друзей: «Хочется поговорить или во что-нибудь поиграть» → заведения/настолки/квиз по времени.
- Компания: «Хочется движухи, но без сильной физической нагрузки» → караоке/настолки/квиз/боулинг.
- Семья: «Пойдём с ребёнком» → только возрастно подходящие, доступные и семейные варианты.
- Человек без определённого запроса: «Сам не знаю» → разнообразная подборка, безопасная по заданным ограничениям.
- Гость Казани: «Нужны понятные адреса и маршрут» → карточка места, адрес, карта и ссылка на официальный источник.

## 2. Страницы и маршрутизация

| Route | Назначение | MVP |
|---|---|---|
| `/` | Главная: три пути, объяснение ценности | да |
| `/quiz` | Основной тест: одна страница со step-компонентом и back | да |
| `/results?session=...` | Результаты текущей анкеты; ссылки с безопасным токеном | да |
| `/explore` | Каталог: события, места, активности; табы и фильтры | да |
| `/places/[slug]` | Карточка постоянного места | да |
| `/events/[slug]` | Карточка события / сеанса | да |
| `/activities/[slug]` | Карточка домашней или самостоятельной идеи | да |
| `/date` | Независимая точка входа будущего теста свиданий | заглушка |
| `/admin` | Защищённый доступ редактора каталога | да |
| `/admin/places`, `/admin/events`, `/admin/activities` | CRUD с публикацией и черновиками | да |

**Общие UI-состояния:** загрузка; ошибка сети + «Повторить»; пустые результаты; истёкшая сессия; отсутствие подходящих событий; недоступный контент; мобильный back/forward. Сохранять ответы теста локально как черновик (sessionStorage либо localStorage с TTL); серверную сессию создавать при выдаче результата. Не помещать ответы в открытый URL.

## 3. Концепция пользовательского пути

```text
HOME
 ├─ /quiz → COMMON.Q1 → Q2 → Q3 → Q4 → DIRECTION
 │                 → BRANCH.<id> → CONSTRAINTS.DATE → BUDGET
 │                 → (conditional CHILDREN/PARTY_SIZE/MOBILITY)
 │                 → RESULTS → CARD → EXTERNAL SOURCE
 ├─ /explore → filters → place/event/activity → external source
 └─ /date → separate module placeholder (no use of MainQuiz state)
```

**Принципы UX:** обычно 7–9 экранов, максимум 11 с условными уточнениями; один вопрос на экран; большие кнопки с короткими подписями; индикатор «ещё пару вопросов» вместо ложного фиксированного процента; кнопка «Назад» на всех шагах кроме первого; нет принудительной регистрации; клавиатурная навигация; отдельная кнопка «Неважно / удивите меня» там, где имеет смысл. На вопросах с несколькими вариантами явно обозначать выбор нескольких, но MVP использует single-select, кроме явно помеченных полей.

## 4. Модель состояния теста

```ts
type SocialEnergy = 'high'|'medium'|'low'|'any';
type Companion = 'solo'|'friend'|'group'|'family'|'partner';
type Mood = 'excitement'|'discovery'|'relax'|'connection'|'surprise';
type Setting = 'outside'|'indoor'|'home'|'any';
type Direction = 'walks'|'venues'|'games'|'culture'|'wellness'|'home';
type DayChoice = 'today'|'tomorrow'|'weekend'|'date';
type BudgetTier = 'free'|'low'|'mid'|'high'|'any';
type BudgetBasis = 'per_person'|'total';
type Transport = 'walking_transit'|'car'|'any';
type GameStyle = 'mind'|'physical'|'digital'|'social'|'surprise';
type Competition = 'competitive'|'friendly'|'cooperative'|'any';

type QuizAnswers = {
  socialEnergy?: SocialEnergy;
  companion?: Companion;
  mood?: Mood;
  setting?: Setting;
  direction?: Direction;
  branchAnswers?: Record<string,string>;
  dayChoice?: DayChoice;
  targetDate?: string;             // ISO local date YYYY-MM-DD
  budgetTier?: BudgetTier;
  budgetBasis?: BudgetBasis;
  partySize?: number;
  childAgeBands?: ('0-3'|'4-6'|'7-12'|'13-17')[];
  transport?: Transport;
};
```

**State machine:** currentStepId, answers, visitedStepIds (история), schemaVersion. Удаление/изменение прежнего ответа должно удалять все зависимые последующие ответы и пересчитывать маршрут. Состояние не должно содержать «запретных» значений или несовместимых комбинаций. Все идентификаторы задаются в конфигурации, UI-текст хранится отдельно от бизнес-значений. Версионировать `quizSchemaVersion`.

## 5. Общие вопросы: точные тексты и ответы

### COMMON.Q1 — настроение общения (обязательный)
**Вопрос:** «Как у тебя сегодня с социальной батарейкой?»
- `high`: «Хочу людей и движухи»
- `medium`: «Только свои, пожалуйста»
- `low`: «Хочу побыть наедине»
- `any`: «Сам пока не понимаю»
**Переход:** всегда COMMON.Q2. Не выводить companion автоматически из ответа.

### COMMON.Q2 — компания (обязательный)
**Вопрос:** «Кого берём с собой в это маленькое приключение?»
- `solo`: «Я сегодня сам по себе»
- `friend`: «С другом или подругой»
- `group`: «Собираемся компанией»
- `family`: «С семьёй / с детьми»
- `partner`: «Вдвоём с близким человеком»
**Переход:** всегда COMMON.Q3. `partner` не запускает сценарий свиданий. Если есть дети, их возраст уточняется перед результатами.

### COMMON.Q3 — эмоциональный результат (обязательный)
**Вопрос:** «Представь, что вечер уже закончился. Что хочется сказать?»
- `excitement`: «Вот это мы оторвались!»
- `discovery`: «Давно так не вдохновлялся»
- `relax`: «Как же хорошо отдохнул»
- `connection`: «Как классно посидели и поболтали»
- `surprise`: «Неожиданно, но было круто!»
**Переход:** всегда COMMON.Q4.

### COMMON.Q4 — окружающая среда (обязательный)
**Вопрос:** «Куда сегодня тянет — подышать воздухом или спрятаться от мира?»
- `outside`: «На улицу, хочу свежего воздуха»
- `indoor`: «Под крышу, в тепло и уют»
- `home`: «Никуда не пойду, хочу дома»
- `any`: «Неважно, лишь бы было интересно»
**Переход:** для `home` сразу `BRANCH.HOME.H1` (не предлагать внешние заведения); иначе `COMMON.DIRECTION`.

### COMMON.DIRECTION — адаптивное меню (обязательный, если setting != home)
**Вопрос:** «Кажется, я уловил настроение! К чему больше тянет?»
Показывать **до четырёх** направлений, основанных на предыдущих ответах; всегда обеспечивать минимум два подходящих варианта. `direction` сохраняется только по явному нажатию. Ни один из вариантов не выбирается алгоритмом без участия человека.

Доступные направления и подписи:
- `walks`: «Прогуляться и сменить картинку»
- `venues`: «Посидеть в интересном месте»
- `games`: «Поиграть и посоревноваться»
- `culture`: «Впечатлиться чем-то новым»
- `wellness`: «Спокойно перезагрузиться»
- `home`: здесь скрыто, потому что домашняя ветка выбирается в Q4

**Детерминированный расчёт вариантов:** базовые баллы 0 для walks/venues/games/culture/wellness. `outside`: walks +5; `indoor`: venues +2, games +2, culture +2, wellness +2; `high`: games +3, venues +2; `medium`: venues +2, games +1; `low`: walks +2, wellness +2, culture +1; `excitement`: games +4; `discovery`: culture +4, walks +1; `relax`: wellness +4, walks +2; `connection`: venues +4, games +1; `surprise`: culture +2, games +2. Сортировка по баллам, затем постоянный tie-break [games, venues, walks, culture, wellness]. Для `outside` не показывать strictly-indoor направления, кроме случаев, когда пользователь выбрал `any` (тут ограничения снимаются); для `indoor` не показывать walks. Для `outside` доступно меньше категорий — показывать также outdoor games/active при наличии в каталоге и не исключать их из `games`. Если после ограничения меньше двух направлений, добавить «Покажи другие идеи» как действие, расширяющее список; не выдумывать несуществующий каталог. Интерактивный переключатель «Показать все направления» обеспечивает свободный выбор любого допустимого направления с предупреждением о несоответствии предпочтению.

**Переход:** `walks -> BRANCH.WALKS.W1`, `venues -> BRANCH.VENUES.V1`, `games -> BRANCH.GAMES.G1`, `culture -> BRANCH.CULTURE.C1`, `wellness -> BRANCH.WELLNESS.R1`.

## 6. Тематические ветки: все вопросы, ответы и переходы

## 7. Общие вопросы после ветки

### COMMON.DATE
**Вопрос:** «Когда устраиваем приключение?»
- `today`: «Сегодня» → BUDGET; targetDate определяется по timezone `Europe/Moscow` (Казань UTC+3) на сервере при запросе, не по часам клиента.
- `tomorrow`: «Завтра» → BUDGET; дата в часовом поясе Казани.
- `weekend`: «В ближайшие выходные» → BUDGET; диапазон суббота–воскресенье, если сейчас выходной — текущие оставшиеся дни (описать UI).
- `date`: «Выбрать дату» → DATE_PICKER → BUDGET.
**DATE_PICKER:** выбирается ISO-дата не раньше сегодняшней для событий. Для постоянных мест/домашних идей допускаются будущие даты; если нет достоверного графика — показывать «проверьте часы работы».

### COMMON.BUDGET
**Вопрос:** «Насколько готовы разгуляться?»
- `free`: «Бесплатно» — 0 ₽
- `low`: «До 1 000 ₽»
- `mid`: «До 3 000 ₽»
- `high`: «До 5 000 ₽»
- `any`: «Неважно, если оно того стоит»
Для `friend`, `group`, `family`, `partner` показывать BASIS: «Этот бюджет на человека или на всех?» `per_person` / `total`; для `solo` автоматически `per_person`. Не подменять неизвестную цену значением 0. Если цена неизвестна, помещать в блок «Стоимость уточняется» ниже уверенно подходящих вариантов.

### COMMON.PARTY_SIZE (условный)
Показывать, если `companion=group` или для специфического формата требуется точное число участников. **Вопрос:** «Сколько вас будет?» Число 3–30 (в MVP); при `friend` =2, `solo`=1, `partner`=2. Для `family` спросить «Сколько всего человек?» (1–30) и CHILD_AGES. Размер группы 1 в family возможен только если пользователь вернулся и изменил companion.

### COMMON.CHILD_AGES (условный)
Если family и дети есть: «Какого возраста дети?» Multi-select: 0–3, 4–6, 7–12, 13–17, «Без детей». При «Без детей» остальные выбранные возрастные группы очищаются. Для нескольких детей разных возрастов объекты должны подходить каждой выбранной группе, иначе маркировать совместимость частичной.

### COMMON.TRANSPORT (условный)
Показывать, если выбран `walks.escape`, `walks.outskirts` или система хочет рекомендовать загородную активность. **Вопрос:** «Как будем добираться?» `walking_transit` «Пешком / общественный транспорт»; `car` «На машине»; `any` «Любым способом». Загородные варианты без возможности добраться выбранным способом исключить, если данные доступны; иначе не гарантировать доступность.

**Порядок завершающих экранов:** DATE → DATE_PICKER (при необходимости) → BUDGET → BASIS (при необходимости) → PARTY_SIZE (если требуется) → CHILD_AGES (если family) → TRANSPORT (если требуется) → RESULTS. Не менять порядок от рендера к рендеру.

## 8. Проверки совместимости и обработка конфликтов

1. `socialEnergy=low` + `companion=group`: разрешено; показать спокойные варианты для компании, не менять ответы пользователя.
2. `setting=home` + `mood=excitement`: разрешено; предлагать домашние игры, не городской клуб.
3. `setting=outside` + `direction=venues`: обычный список не показывает indoor-only; разрешить явно включить «Другие варианты» и пометить несоответствие.
4. `companion=solo` + командный квест с `minParticipants=4`: исключить, кроме если явно есть присоединение к сборной группе и `joinOpenGroup=true`.
5. Семья с детьми + adult-only/бар 18+: исключить независимо от высокого рейтинга.
6. Прогноз плохой погоды: не удалять все outdoor варианты автоматом; пометить риск и опустить в выдаче, при опасной погоде выдавать предупреждение и безопасные indoor альтернативы с запросом подтверждения смены setting.
7. Событие прошло, распродано или нет сеанса на выбранную дату: исключить из бронируемых рекомендаций; опубликованная карточка может остаться в каталоге только с правильным статусом.
8. Цены неизвестны: не выдумывать, отдельно показывать «Цена уточняется»; не считать бесплатными.
9. Если направление отсутствует в каталоге, отображать альтернативные категории с ясной маркировкой «Похожие идеи», не показывать пустую ошибку.
10. Изменение ответа в прошлом шаге очищает устаревшие branchAnswers, DATE и зависимые фильтры, но может сохранить независимые поля при корректной валидации — предпочтительнее простая полная очистка последующих шагов.
11. Дата на сервере, timezone `Europe/Moscow`, не timezone пользователя. События с временными интервалами хранить timezone-aware.
12. Нельзя одновременно присваивать `dateQuiz` и `mainQuiz` одной сессии. Route `/date` использует другую schema ID.

## 9. Алгоритм рекомендаций (MVP, без генеративного AI)

**Шаг 1 — собирать кандидатов** из `places`, `events` и `activities`, только `status=published`, актуальных и допустимых по виду досуга.

**Шаг 2 — жёсткая фильтрация:** валидность даты/сеанса; возраст; вместимость; indoor/outdoor/home (кроме явно включённого расширения); логистика при известной недоступности; бюджет с известной точной стоимостью, если превышение — исключить; статус `cancelled` / `sold_out`. Для мест без цены считать цену неизвестной, а не 0.

**Шаг 3 — мягкая оценка от 0 до 100:**
- совпадение выбранного направления/подвида — 35;
- настроение — 20;
- состав компании — 15;
- энергия/интенсивность — 10;
- желаемая атмосфера — 10;
- близость по бюджету — 5;
- качество и полнота данных — 5.
Для `any` нейтральное, а не отрицательное значение. Баллы вычисляются по таблицам тегов и нормализуются на применимые критерии. При неизвестных тегах не считать совпадение доказанным. Вторичный tie-break: опубликованная дата обновления, затем стабильный id. Разнообразие: не более двух первых карточек одной узкой подкатегории, если существует альтернатива с баллом в пределах 15. Число главных результатов — до 7, при наличии минимум 3; если меньше, честно показать меньше.

**Шаг 4 — fallback:** расширить только мягкие параметры, затем соседние подкатегории; никогда не отменять возраст, дату, вместимость и строгий бюджет без подтверждения пользователя. Показывать, какие критерии были смягчены. Если 0 вариантов — пустой экран с кнопками изменить дату, бюджет, тип активности, открыть каталог.

**Шаг 5 — объяснение:** каждая карточка показывает «Почему подходит» на основе конкретных совпадений (например, «Для компании · В помещении · До 3 000 ₽»), но никогда не заявляет наличие мест, если это не подтверждено внешней системой.

**Погода:** интеграция может отсутствовать в MVP. При отсутствии достоверного прогноза вывести нейтральное «Проверьте погоду перед прогулкой», не изображать прогноз. Если будет провайдер, сохранять время получения и источник; при ошибке API продолжать работу без погоды.

## 10. Схема каталога и данные

Основные таблицы PostgreSQL (Supabase + Drizzle ORM или Prisma, выбрать одну и закрепить):

- `places`: id, slug, title, description, address, lat, lng, district, contacts, websiteUrl, bookingUrl?, openingHoursJson?, priceMin?, priceMax?, priceCurrency='RUB', priceUnit, ageMin?, minParticipants?, maxParticipants?, indoorOutdoor, durationMinutes?, status, sourceUrl, verifiedAt?, publishedAt, updatedAt.
- `events`: id, placeId?, slug, title, description, startsAt, endsAt?, timezone='Europe/Moscow', priceMin?, priceMax?, ticketsUrl?, status (`draft|published|cancelled|sold_out|archived`), sourceUrl, verifiedAt?, publishedAt, updatedAt, capacity?, ageMin?. Один повторяющийся формат мероприятия может иметь отдельные `event_occurrences` для нескольких сеансов.
- `activities`: id, slug, title, description, stepsRichText, durationMinutes?, costMin?, costMax?, requiredMaterialsJson?, minParticipants?, maxParticipants?, status, sourceUrl?, publishedAt, updatedAt; местоположение = `home`.
- `tags`: id, key, label, group (`category|mood|energy|company|format|setting|accessibility|physicalLoad|gameStyle|competitionMode`); `content_tags`: contentType, contentId, tagId (уникальные тройки).
- `media`: id, contentType, contentId, url, alt, order, rightsStatus; изображения только с правами/разрешением.
- `quiz_sessions`: id (UUID), publicTokenHash, schemaVersion, quizType, answersJson, createdAt, expiresAt. TTL 30 дней; минимизировать данные, не собирать ФИО и контакты.
- `recommendation_logs` (опционально): sessionId, contentType, contentId, score, reasonCodes, createdAt; агрегировать без персональных данных.
- `admin_users`: userId Supabase auth, role (`editor|admin`), createdAt; защищать RLS / server authorization.

**Обязательные поля при публикации:** title, slug, description, category/tags, status, dataSource/sourceUrl (для мест и событий), location/address для places, временная метка/интервал для событий. `verifiedAt` и ссылка на первоисточник — обязательны перед попаданием события в актуальную подборку; данные на внешних площадках всё равно могут измениться. Админка должна поддерживать manual unpublish, preview, фото, теги, дату, цену, возраст, размер группы и модерацию.

**Разделение сущностей:** `place` — постоянная площадка, `event` — конкретное событие в дату/время, `activity` — самостоятельная идея (например, дома). Один и тот же ресторан как place и ужин-квиз как event могут сосуществовать и ссылаться друг на друга.

## 11. API и контракт функций

- `GET /api/catalog?type=place|event|activity&date=...&category=...&priceMax=...&page=...` — пагинированная выдача, валидация query, лимит.
- `GET /api/places/:slug`, `GET /api/events/:slug`, `GET /api/activities/:slug` — только опубликованные публично.
- `POST /api/quiz/validate-step` — опционально; клиентская схема общая с сервером, нет бизнес-правил только в UI.
- `POST /api/quiz/complete` — Zod валидирует schemaVersion, тип теста, обязательные и условные поля; возвращает `{ sessionToken, results, relaxedFilters, reasons }`.
- `GET /api/results/:token` — восстановить результаты по короткоживущему непрозрачному токену; rate limit.
- `POST /api/admin/*`, `PATCH /api/admin/*`, `DELETE /api/admin/*` — CRUD с auth и RBAC; лог изменений.

**Ошибка:** одинаковый envelope `{error:{code,message,details?}}`; коды `INVALID_ANSWER`, `STALE_QUIZ_VERSION`, `CONTENT_NOT_FOUND`, `NO_RESULTS`, `RATE_LIMITED`, `UNAUTHORIZED`. Не возвращать внутренние ключи и stack trace клиенту. Ограничить запросы и санитаризировать rich text.

## 13. Конфигурация графа: строгие правила

- Каждый вопрос: `id`, `kind`, `title`, `options[]`, `visibilityRule`, `nextStep`/`nextStepResolver`, `writesTo`, `required`.
- `stepId` глобально уникален (`COMMON.Q1`, `BRANCH.GAMES.G2_MIND`). `option.value` уникален внутри вопроса.
- `nextStepResolver` — чистая функция от валидного `QuizAnswers`; никаких LLM или внешней сети.
- Имеется один terminal `RESULTS`. Граф не содержит циклов и недостижимых узлов (кроме намеренно скрытого DATE Quiz).
- У каждого visible вопроса >= 2 ответа; каждое значение по своему типу; все ветки заканчиваются в RESULTS.
- Изменение ответа в предыдущем шаге сбрасывает downstream-state на основе dependency graph; нельзя сохранять G2_PHYSICAL после перехода в G2_DIGITAL.
- Схема доступна для unit test, state serializable (без функций в persist payload), `schemaVersion` обязателен.
- Draft quiz восстанавливается после reload, с предупреждением при несовместимой версии и возможностью начать заново.

## 14. План тестирования: must-pass

### Unit tests
1. Проверить все допустимые значения каждого вопроса и переходы, включая G1→все G2→G3.
2. Проверить, что для `COMMON.Q4=home` невозможно попасть в внешние ветки без изменения Q4.
3. Сгенерировать все комбинации основных Q1×Q2×Q3×Q4 (4×5×5×4=400) и проверить доступность terminal RESULTS, отсутствие зависаний и валидный direction menu для всех не-home случаев.
4. Для каждого G2 subtype проверить сохранение ответа и невозможность лишнего subtype.
5. Проверить back/change-answer, очищение downstream, сериализацию/reload, stale schemaVersion.
6. Фильтрация: child-age, minParticipants, maxParticipants, adult-only, отменённое событие, дата, zero price vs unknown, home-vs-venue.
7. Проверить timezone Казани вблизи полуночи 23:59/00:01 и границ выходных.
8. Проверить empty results, fallback, sorting ties deterministic и разные категории в первой выдаче.

### Integration/E2E
- Пользователь один → тихая прогулка → сегодня → бесплатно → видит подходящие outdoor карточки.
- Компания 6 человек → игры → интеллект → квиз → дружеский азарт → weekend → до 3000 на человека → доступны только совместимые слоты.
- Семья с детьми 4–6 лет → indoor → игры → exclude 18+.
- Домашний вечер → домашние активности; никогда не ресторан.
- Назад с G2_MIND на G1, изменить на digital → показывается G2_DIGITAL; прежние mind-ответы очищены.
- Попытка вручную отправить invalid JSON/sessionToken → корректная ошибка.
- Недоступный API погоды и отсутствие контента не ломают интерфейс.
- `/date` никак не наследует ответы `/quiz`.
- Анонимный пользователь не может войти в admin или получить черновики.

### Accessibility + качество
Keyboard-only, screen reader labels, фокус после переключения вопроса, мобильная viewport проверка, responsive, typecheck, lint, тесты, production build и basic performance. У изображений alt и placeholder. На карточках нет фиктивных фото/цен.
